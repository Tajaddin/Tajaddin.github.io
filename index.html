LLM agents · evaluation

Autonomous bug-fix agent

12/12 bugs fixed on Claude Haiku 4.5, 3.58 iterations per bug, $0.10 for the whole sweep

⌄

Challenge

Get an LLM to fix real Python bugs with evidence rather than confidence: the fix has to pass the repository's own pytest, within a bounded number of iterations and tokens, and the agent must not be able to edit the tests.

Architecture

A tool loop on the Anthropic Agent SDK with five tools: list_dir, read_file, edit_file (a str_replace that refuses ambiguous matches), search_code and run_tests. Each attempt runs in an isolated temporary workspace. A MockLLM returns the same (content, stop_reason, usage) shape as the real client, so the whole pipeline is testable without an API key.

Solution

The agent reads, edits and runs the tests; it stops at the first PASS or when the iteration budget runs out. The test file is held back from edits by instruction and the harness records every tool call, token and dollar per bug.

Implementation

Python. Twelve hand-built bugs (off-by-one, mutable default argument, shallow copy, inverted condition and so on), each with three or four assertions. The benchmark writes a JSON record per bug; CI runs the mock sweep on every push. 22 tests.

Verified outcome

Live Claude Haiku 4.5: 12/12 fixed, 3.58 LLM rounds and 5.58 tool calls per bug, $0.10 total (77,457 tokens), from the committed benchmark file of 2026-05-20.live result file The mock pipeline was re-run on 2026-10-16: 12/12.re-run

Data engineering · streaming

Event-time streaming ETL with per-partition watermarks

0% false-late events, down from 71% with a single global watermark; windows match the ground truth exactly

⌄

Challenge

Events arrive out of order across partitions. The first version used one global watermark and, at zero injected lateness, flagged 7,104 of 10,000 in-window events as late. The unit tests passed because they were single-partition.

Architecture

A message bus (in-memory, with a Kafka adapter) drained round-robin per partition, feeding a tumbling-window aggregator and a DuckDB sink with separate windows and late_events tables. A SQLite checkpointer stores per-partition offsets and the watermark floor so a restart never double-emits a closed window.

Solution

A WatermarkTracker keeps the maximum event time per partition; the effective watermark is the minimum across partitions, so a slow partition holds the clock back instead of having its events discarded. Genuinely late events go to a side output rather than being dropped.

Implementation

Python with DuckDB and SQLite. Writes run in explicit transactions per batch, which measured about three times faster than DuckDB's per-statement autocommit on this workload. 25 tests.

Verified outcome

50,000 events, 4 partitions, 50 keys: 0% false-late against 71% for the naive version, and 2,550 windows emitted, which matches the ground truth.re-run Throughput is machine-dependent: 4,566 events/s in the README run, 7,450/s re-run on Linux, and about 480/s on a Windows PC whose antivirus slows file I/O, so the headline is the correctness number, not the rate.

Machine learning · data quality

Fake-news detection: a leakage audit

62.1% accuracy, 0.676 ROC-AUC on the held-out LIAR test set, replacing a 99 to 100% number that came from leakage

⌄

Challenge

On the usual fake-vs-real news corpus, plain logistic regression scored 99 to 100% on the test set out of the box. A result that good on a hard task is normally a sign the data is leaking the label.

Architecture

A six-step audit script: dataset size check, train/test text overlap, label-leaking metadata (publisher names, datetime artifacts, URL fragments), a random-label baseline, the train-versus-test gap, and seed sensitivity. The pipeline itself is TF-IDF (1 to 2-grams) plus logistic regression, with a Hugging Face transformer baseline, SHAP and LIME explanations and MLflow tracking.

Solution

The audit traced the accuracy to publisher and stylistic leakage, so the reported number moved to LIAR, a short-statement dataset, using the statement and its context only and no speaker identity, which would otherwise act as a label.

Implementation

Python and scikit-learn. CI downloads LIAR, builds the splits and re-evaluates on every push. On 2026-10-16 a 25-test suite was added, including a regression test on the reported metric; it immediately found a bug in the feature extractor (it crashed on any frame without a title column), which is fixed.

Verified outcome

62.1% accuracy, 0.676 ROC-AUC on 1,267 held-out LIAR statements, reproduced exactly from a fresh clone on 2026-10-16.re-run It is deliberately an unimpressive number; the point of the project is knowing why the impressive one was wrong.

Distributed systems · reliability

At-least-once webhook delivery

99.92% eventual delivery under 30% injected transient failures, with nothing left stuck, in a deterministic simulation

⌄

Challenge

Deliver webhooks at least once with bounded retries, no duplicate sends, signed payloads and a dead-letter queue for endpoints that never recover, and prove the guarantee instead of asserting it in a README.

Architecture

A Hono API with a background drain loop over an in-memory delivery queue keyed by idempotency key. A worker state machine moves each delivery from pending to delivered, back to pending with exponential backoff and full jitter, or to dead after the attempt budget. Payloads carry a Stripe-style t=,v1= HMAC-SHA256 signature verified in constant time with a replay window. The clock and the random source are injectable.

Solution

A VirtualClock makes backoff waits instant, so the full retry and dead-letter behaviour runs in milliseconds. The fault-injection benchmark enqueues 20,000 deliveries against a fake transport with a 30% failure rate per attempt and 2% permanently dead endpoints, then drains to completion under the default six-attempt policy.

Implementation

TypeScript in strict mode with noUncheckedIndexedAccess, Vitest (21 tests), Docker and GitHub Actions.

Verified outcome

99.92% of deliverable messages delivered: 19,551 delivered, 449 dead-lettered (434 permanently down plus 15 that exhausted retries), 0 stuck pending.re-run This is an in-process simulation with a seeded random generator, a virtual clock and no network.simulated The dispatch rate it prints (about 21,000/s in the README, 58,000/s on this machine) measures the loop, not HTTP delivery, so it is not quoted as throughput.

GPU computing · correctness

GPU index nested-loop join with a B+ tree

Join kernel 4.4x faster than a GPU hash-join kernel, after fixing a bug that silently dropped 1.5% of matches

⌄

Challenge

Join two tables of up to 10 million rows on the GPU with an index: one thread per outer-table tuple walks a B+ tree over the inner table, with results compacted into one contiguous array.

Architecture

The B+ tree is bulk-loaded on the host and copied to the device with node layouts aligned to warp boundaries. The probe kernel writes matches into per-block buffers that a prefix-sum pass compacts. A CPU reference join checks match counts, and a GPU hash join (build and probe kernels) is the performance baseline.

Solution

On 2026-10-16 the correctness test showed the GPU join returning 49,227 matches where the CPU reference returned 50,000. The separator keys were wrong in trees of height three or more, so some probes descended into the wrong subtree. With the fix the counts match on every selectivity level.

Implementation

CUDA C++ built for sm_60 through sm_86, with a four-test driver (correctness, performance, scalability from 100K to 10M rows, selectivity from 10% to 100% overlap) and Nsight profiling targets.

Verified outcome

Probe kernel 0.54 ms versus 2.34 ms for the hash-join kernel at 1M x 1M rows and 50% overlap on an RTX 4060.re-run End to end the hash join still wins by about 20x at 10M rows, because the tree is built on the CPU while the hash table is built on the GPU; the index join only pays off when one index is probed many times. Earlier claims of a 4.2x speed-up over the CPU and of near-peak memory bandwidth had no measurement behind them and were removed.
